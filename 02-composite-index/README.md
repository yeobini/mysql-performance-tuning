# 복합 인덱스와 커버링 인덱스

## Objective

복합 인덱스를 생성하면 검색 속도가 빨라지는지, 빨라진다면 얼마나 빨라지는지 측정한다.

첫 번째 단계(단일 컬럼 인덱스)에서는 쿼리문의 조건이 하나였고, 그래서 그 해당 컬럼만을
인덱스로 만들면 효과를 볼 수 있었다. 쿼리문 조건이 복잡해진다면 복합 인덱스를 생성해야
한다고 생각했다.

비교 대상은 두 가지다.

- FK로 자동 생성된 인덱스만 있는 상태
- 복합 인덱스를 생성한 상태

> 측정을 시작할 때의 계획은 위 두 가지 비교였다.
> 커버링 인덱스는 2단계에서 개선이 나타나지 않아 원인을 찾는 과정에서 추가된 것이다.

## Design Note

### 복합 인덱스를 만들었는데 왜 빨라지지 않았는가

쿼리문 자체가 전체 컬럼을 가져오는 것(`SELECT *`)이 원인이었다.

1단계에서는 FK로 자동 생성된 인덱스(`member_id`)로 `member_id = 1`인 행 3,650건을 찾고,
그 행들의 PK인 `order_id`로 테이블을 다시 찾아가 나머지 컬럼들을 가져와야 했다.
`order_status`가 인덱스에 없어서, '배송완료'인지 확인하려면 일단 가져와야 하기 때문이다.
이렇게 두 번 훑는 과정이 북마크 룩업이다.

그 후 가져온 행들 중 `order_status`가 '배송완료'인 2,552건을 반환한다.
이 걸러내는 작업에 걸린 시간은 단 0.7ms, 전체 11.8ms의 6%에 해당한다.

```
-> Filter: (order_status = '배송완료')         (actual time=1.16..11.8  rows=2552)
     -> Index lookup on orders using member_id   (actual time=1.15..11.1  rows=3650)

Filter 자기 몫 = 11.8 - 11.1 = 0.7ms
```

`EXPLAIN ANALYZE`의 `actual time`은 자식 노드의 시간을 포함한 누적값이므로, 각 단계가
쓴 시간은 빼서 구한다. `Filter`의 11.8ms와 `Index lookup`의 11.1ms를 더해 22.9ms로
읽으면 안 된다. 전체 쿼리 시간은 가장 바깥 노드의 값이다.

| | 누적인가 |
|---|---|
| `rows` | 아니다. 각 노드의 출력값 |
| `actual time` | 그렇다. 자식 시간 포함 |

복합 인덱스가 제거하는 것은 이 6% 구간이다. 나머지 94%는 테이블에서 전체 컬럼을
가져오는 작업이고, 복합 인덱스를 만들어도 `SELECT *`는 그대로이므로 이 작업은 사라지지
않는다. 읽을 행수는 3,650 → 2,552로 줄었지만, 조건에 해당하는 행을 뽑고 전체 컬럼을
다시 가져오는 반복 작업은 그대로 남는다.

측정 결과 11.8ms → 13.8ms. 개선이 없었다.

### 북마크 룩업이 필요한 이유는 단계마다 다르다

| | 북마크 룩업하는 이유 | 횟수 |
|---|---|---|
| 1단계 | ① `order_status` 확인 (인덱스에 없음)<br>② 전체 컬럼 조회 | 3,650 |
| 2단계 | ② 전체 컬럼 조회 | 2,552 |
| 3단계 | 없음 | 0 |

1단계에서는 조건 확인 자체를 위해 테이블에 가야 했다. 인덱스만으로는 '배송완료'인지
알 수 없으므로, 조건에 맞지 않는 1,098건도 일단 가져와야 했다.

2단계에서 `order_status`가 인덱스에 들어오면서 ①이 사라졌다. 조건이 인덱스에서 모두
처리되므로 조건에 맞는 2,552건만 가져간다. `filtered`가 10% → 100%로 바뀌고 `Filter`
노드가 사라진 것이 그 증거다.

남은 것은 ②뿐이고, 이것은 `SELECT *`가 `order_date`, `total_price`를 요구하기 때문이다.
인덱스를 어떻게 만들어도 해결되지 않는다.

### 커버링 인덱스

그래서 `SELECT`문을 수정한다. 즉 `SELECT` 전체 컬럼이 아닌, 인덱스에 해당되는 컬럼들만으로.
그랬더니 시간은 확연히 줄었다. 그 이유는 북마크 룩업이 사라지기 때문이다.

이 인덱스에는 `member_id`, `order_status`, `order_id` 세 컬럼이 들어있다.
`order_id`는 지정하지 않았지만 PK이므로 세컨더리 인덱스 리프에 자동으로 포함된다.
이 세 컬럼만 조회하면 인덱스만 읽고 답을 만들 수 있어 테이블에 갈 필요가 없다.

3단계에서는 인덱스를 새로 만들지 않았다. `SELECT` 목록만 바꿨다.
원인이 인덱스가 아니라 쿼리 쪽에 있었기 때문이다.

### key_len으로 두 컬럼이 모두 쓰이는지 확인한다

| | 1단계 | 2단계 |
|---|---|---|
| `key_len` | 8 | 90 |
| `ref` | `const` | `const,const` |

```
member_id    BIGINT NOT NULL                        8
order_status VARCHAR(20) NOT NULL utf8mb4   20×4 + 2 = 82
                                                  ----
                                                    90
```

`VARCHAR(20)`의 20은 글자 수이고 바이트 수가 아니다. utf8mb4는 한 글자 최대 4바이트이므로
선언 시에는 최악을 가정해 80바이트로 계산한다. +2는 가변 길이 값의 길이를 저장하는 공간이다.
`NOT NULL`이므로 NULL 표시용 1바이트는 붙지 않는다.

`key_len`이 8에서 90으로 늘어난 것이 두 컬럼을 모두 사용하고 있다는 증거다.
8에 머물렀다면 후행 컬럼을 쓰지 못하고 있다는 뜻이다. `ref`가 `const`에서 `const,const`로
바뀐 것도 같은 사실을 보여준다.

`key_len`은 옵티마이저가 인덱스에서 최대 몇 바이트까지 쓸 수 있는지를 나타내는 값이며,
실제 저장 크기가 아니다. 실제 저장 크기는 측정으로 구했다.

```
75.7MB ÷ 2,000,000건 = 약 40바이트/건
```

### 디스크에 가지 않아도 느릴 수 있다

`SHOW STATUS LIKE 'Innodb_buffer_pool_read%'`를 쿼리 전후로 찍어 비교한 결과,
두 쿼리 모두 디스크 읽기(`Innodb_buffer_pool_reads`) 증가분이 0이었다.
캐싱은 이루어지고 있었던 것이다. 그럼에도 `SELECT *`는 13.8ms가 걸렸다.
북마크 룩업 때문이다.

| | 페이지 요청 | 디스크 읽기 | 시간 |
|---|---|---|---|
| `SELECT *` | +8,668 | +0 | 13.8ms |
| 커버링 | +31 | +0 | 1.13ms |

8,668번은 2,552건 × `PRIMARY` B-Tree 3단계 탐색에 해당한다 (8,668 ÷ 2,552 = 3.4).
전부 메모리에서 처리됐지만, 메모리 접근도 공짜가 아니므로 1만 번 가까이 반복하면
ms 단위가 쌓인다.

"쿼리가 느리다 = 디스크 I/O"로 단정할 수 없다.

## Result

| | 1단계 | 2단계 | 3단계 |
|---|---|---|---|
| 인덱스 | FK 자동 `member_id` | 복합 `(member_id, order_status)` | 동일 |
| 쿼리 | `SELECT *` | `SELECT *` | 인덱스 컬럼만 |
| `type` | `ref` | `ref` | `ref` |
| `key_len` | 8 | 90 | 90 |
| `rows` 추정 | 3,650 / `Filter` 365 | 2,552 | 2,552 |
| `filtered` | 10.00% | 100.00% | 100.00% |
| `Extra` | `Using where` | `NULL` | `Using index` |
| 트리 노드 | `Filter` + `Index lookup` | `Index lookup` | `Covering index lookup` |
| 테이블 액세스 | 3,650회 | 2,552회 | **0회** |
| 페이지 요청 | — | 8,668 | **31** |
| 디스크 읽기 | — | 0 | **0** |
| `cost` | — | 2,160 | **287** |
| 시간 (중앙값) | 11.8ms | 13.8ms | **1.13ms** |
| 결과 행 | 2,552 | 2,552 | 2,552 |

결과 행이 세 단계 모두 2,552로 동일하다. 달라졌다면 측정이 잘못된 것이다.

1단계 → 2단계: 개선 없음 (전체 시간의 6%를 차지하는 구간을 제거)
2단계 → 3단계: 12배 (94%를 차지하는 구간을 제거)

### 측정 변동 폭

각 단계를 5회 측정했다. (1단계는 1회 측정값이다)

| | 측정값 | 중앙값 | 폭 | 중앙값 대비 |
|---|---|---|---|---|
| `SELECT *` | 9.39 / 10.4 / 13.8 / 15.2 / 17.4 | 13.8ms | 8.0ms | 58% |
| 커버링 | 1.07 / 1.08 / 1.13 / 1.13 / 1.15 | 1.13ms | 0.08ms | 7% |

페이지 요청이 8,668번에서 31번으로 줄면서 변동 폭도 함께 줄었다.
접근 횟수가 많을수록 변동이 커지는 것으로 보이지만, 원인을 분리해서 측정하지는 못했다.

### 인덱스 Cardinality

| `Seq_in_index` | 컬럼 | `Cardinality` |
|---|---|---|
| 1 | `member_id` | 172,218 |
| 2 | `order_status` | 438,900 |

`Cardinality`는 그 컬럼 하나의 고유값 수가 아니라, 1번부터 그 줄까지 누적한 조합의
고유값 수다. 그래서 2번 줄이 1번 줄보다 작으면 비정상이다.

438,900 ÷ 172,218 ≈ 2.5로, 회원 한 명당 평균 2.5종류의 상태를 가지고 있다.

## 실험: FK 자동 인덱스의 생명주기

인덱스 크기를 측정하던 중 `orders`의 인덱스 목록에 `member_id`가 없는 것을 발견했다.
전날 측정에서는 `EXPLAIN`이 `key = member_id`로 이 인덱스를 사용하고 있었다.

`SHOW INDEX`와 `information_schema.statistics`로 교차 확인한 결과 정말 없었다.
직접 만든 적도 지운 적도 없는 인덱스였다. FK를 선언할 때 InnoDB가 자동으로 만든 것이었다.

> 복합 인덱스를 만들 때 해당 컬럼이 FK였는데, 그래서 사라졌나? 싶었다.

가설을 세웠다. 복합 인덱스 `(member_id, order_status)`의 선두 컬럼이 `member_id`이므로
FK를 대신 받쳐줄 수 있게 되었고, InnoDB가 중복이 된 자신의 인덱스를 정리했다는 것이다.

### 재현

`fk_test` 스키마에 빈 테이블로 최소 환경을 만들었다. 부모 테이블 하나, FK를 가진 자식
테이블 하나. 데이터는 0건이다.

| | 만든 복합 인덱스 | FK 자동 인덱스 |
|---|---|---|
| 실험군 | `(FK컬럼, 다른컬럼)` — FK 컬럼 선두 | **사라짐** |
| 대조군 | `(다른컬럼, FK컬럼)` — FK 컬럼 후행 | **남음** |

대조군이 남은 이유는 선두 컬럼 규칙이다. FK 검사는 "이 값이 부모 테이블에 있는가"를
묻는 것인데, FK 컬럼이 후행에 있으면 그것으로 탐색 범위를 좁힐 수 없다.
따라서 FK를 대체할 수 없고, 자동 생성된 인덱스가 계속 필요하다.

### 확증

```sql
DROP INDEX idx_orders_member_status ON orders;
```

```
Error Code: 1553. Cannot drop index 'idx_orders_member_status':
needed in a foreign key constraint
```

현재 이 인덱스가 FK를 받치는 유일한 인덱스이므로 삭제가 거부된다.

### 결론

> InnoDB는 FK 선언 시 인덱스를 자동 생성하고, 그 FK를 대체할 수 있는 인덱스가 생기면
> 자동 생성한 것을 제거한다. 대체 가능 조건은 FK 컬럼이 인덱스의 선두에 있는 것이다.
> 그 인덱스가 FK를 받치는 유일한 인덱스가 되면 삭제할 수 없다.

InnoDB는 사용자가 만든 인덱스에는 손대지 않고, 자신이 만든 것만 넣고 뺀다.

## Troubleshooting

### 측정 환경이 바뀐 것을 모르고 측정할 수 있다

단일 컬럼 인덱스 측정(1장)에서는 전날 스크립트로 만들어둔 인덱스가 남아 있는 상태에서
"인덱스 적용 전"을 측정하려 했다. `EXPLAIN`의 `key` 값을 확인해 발견했다.

이번에는 인덱스를 만든 직후 `SHOW INDEX`로 확인하는 것부터 시작했다.
그 과정에서 `member_id` 인덱스가 사라진 것을 발견했다.

측정 전후로 환경을 확인하지 않으면 "무엇을 측정했는지"를 알 수 없다.
