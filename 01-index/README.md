# 단일 컬럼 인덱스

## Objective

회원 100만 건 테이블에서 이름으로 조회하는 쿼리에 단일 컬럼 인덱스를 적용하고,
그 효과를 추정값이 아닌 **실제 실행시간**으로 측정한다.

소규모 데이터에서는 옵티마이저가 인덱스를 선택하지 않거나, 선택해도 실행시간 차이가
측정되지 않는다. 따라서 100만 건 규모에서 측정한다.

## Environment

| 항목 | 값 |
|---|---|
| MySQL | 8.0.46 |
| 스토리지 엔진 | InnoDB |
| `innodb_buffer_pool_size` | 128MB (기본값) |
| 대상 테이블 | `member` 1,000,000행 |
| 데이터 크기 | 데이터 149.7MB + 인덱스 91.4MB |

데이터는 재귀 CTE로 생성했다. 생성 스크립트는 [`00-setup/`](../00-setup) 에 있으며,
작성에 AI 도구를 활용했다.

## Tasks

1. 측정 대상의 데이터 분포 확인 (전체 건수, 고유값 수, 선택도)
2. 현재 인덱스 목록 확인
3. 인덱스 없는 상태에서 실행계획과 실제 소요시간 측정
4. 인덱스 생성
5. 인덱스 있는 상태에서 동일 측정
6. 인덱스의 저장 비용 확인

측정 대상 쿼리는 전후 동일하게 사용했다.

```sql
SELECT * FROM member WHERE member_name = '김민준';
```

## SQL

### 1. 데이터 분포 확인

```sql
SELECT COUNT(*)                                  AS total_rows,
       COUNT(DISTINCT member_name)               AS distinct_names,
       COUNT(*) / COUNT(DISTINCT member_name)    AS rows_per_name
FROM member;
```

```sql
SELECT member_name, COUNT(*) AS cnt
FROM member
GROUP BY member_name
ORDER BY cnt DESC
LIMIT 5;
```

### 2. 현재 인덱스 확인

```sql
SHOW INDEX FROM member;
```

### 3. 측정

```sql
EXPLAIN SELECT * FROM member WHERE member_name = '김민준';

-- 1회차 (워밍업)
EXPLAIN ANALYZE SELECT * FROM member WHERE member_name = '김민준';
-- 2회차 (기록값)
EXPLAIN ANALYZE SELECT * FROM member WHERE member_name = '김민준';
```

### 4. 인덱스 생성 / 삭제

```sql
CREATE INDEX idx_member_name ON member(member_name);
ANALYZE TABLE member;

DROP INDEX idx_member_name ON member;
```

### 5. 인덱스 저장 비용

```sql
SELECT index_name,
       stat_value                        AS pages,
       ROUND(stat_value * 16 / 1024, 1)  AS size_mb
FROM mysql.innodb_index_stats
WHERE database_name = 'dba_portfolio_perf'
  AND table_name    = 'member'
  AND stat_name     = 'size';
```

## Design Note

### 측정 전에 데이터 분포를 먼저 확인한 이유

인덱스의 효과는 조건이 전체 중 얼마를 걸러내는지에 따라 달라진다.
`member_name`은 성 20종 × 가운데 10종 × 끝 10종으로 생성해 2,000가지 조합이 있고,
100만 건이 그 안에 분포하므로 이름 하나당 500건이다. 전체의 0.05%다.

분포를 모르면 측정값이 나와도 그것이 정상인지 판단할 근거가 없다.
0.05%를 조회하는 조건이라면 큰 개선이 나와야 하고, 만약 차이가 없다면
인덱스를 타지 않았거나 측정 방법이 잘못된 것이다.

### 반환 행은 같고 읽은 행은 다르다

조건에 맞는 회원이 500명이므로 반환되는 행 수는 인덱스 유무와 무관하게 500행으로 같다.
같은 쿼리이므로 결과가 달라지면 그것은 튜닝이 아니라 오류다.

차이는 그 500행을 얻기까지 읽은 행 수에 있다.

| | 읽은 행 | 반환 행 | 버린 행 |
|---|---:|---:|---:|
| 인덱스 전 | 1,000,000 | 500 | 999,500 (99.95%) |
| 인덱스 후 | 500 | 500 | 0 |

인덱스 전에는 전체 100만 행을 읽어 조건에 맞지 않는 99.95%를 버렸다.
실행계획에서도 `Table scan`이 100만 행을 읽고 `Filter`가 500행만 남기는
두 단계로 나타났다. 인덱스 후에는 `Index lookup` 한 단계만 남았고,
인덱스가 조건을 이미 처리했으므로 별도의 필터 단계가 사라졌다.

튜닝은 결과를 바꾸지 않으면서 읽는 양을 줄이는 작업이다.

### 인덱스는 옵티마이저의 판단 재료도 제공한다

인덱스가 없을 때 옵티마이저는 `rows = 99,062`로 추정했다.
이 값은 `990,615 × 10%`로, 전체 행 수에 `filtered` 기본값 10%를 곱한 것이다.
`member_name`에 인덱스가 없어 값의 분포를 알 수 없으므로,
"등치 조건이면 10% 정도가 통과한다"는 기본 가정을 사용한 것이다.

실제는 500행이므로 **198배 과대추정**이다.

인덱스를 생성한 뒤에는 `rows = 500`으로 정확히 추정했다.
인덱스가 카디널리티 통계를 제공하기 때문이다.

즉 인덱스는 조회 속도만 개선하는 것이 아니라, 옵티마이저가 올바른 실행계획을
선택할 수 있도록 통계를 제공한다. 대량 적재 후 `ANALYZE TABLE`을 실행하는 이유도
같다. 통계가 실제 분포와 맞지 않으면 인덱스가 있어도 선택되지 않을 수 있다.

### 개선 효과는 두 겹으로 나타났다

1회차와 2회차의 개선폭이 달랐고, 원인도 서로 다르다.

**1회차 — 읽을 페이지 수가 줄었다 (1010ms → 112ms, 9배)**

인덱스는 정렬된 B-Tree 구조이므로 전체를 훑지 않고 찾아 들어간다.
100만 건에서도 약 3단계면 `'김민준'`의 첫 위치에 도달하고,
정렬되어 있으므로 500개 항목이 연속으로 붙어 있어 순차로 읽으면 된다.

| | 읽은 페이지 |
|---|---:|
| 풀스캔 | 9,580 |
| 인덱스 조회 | 약 503 (B-Tree 3 + 리프 + 데이터 500) |

19배 적게 읽으므로 캐시와 무관하게 1회차부터 빠르다.

**2회차 — 버퍼 풀에 들어갔다 (112ms → 2.36ms, 47배)**

| | 읽는 양 | 버퍼 풀 | 2회차 |
|---|---:|---:|---|
| 인덱스 전 | 149.7MB | 128MB | 1032ms (개선 없음) |
| 인덱스 후 | 약 8MB | 128MB | 2.36ms (47배 개선) |

인덱스 후에 읽는 약 8MB는 버퍼 풀 128MB에 들어간다.
1회차에 디스크에서 읽어 메모리에 올려두었으므로, 2회차는 디스크에 접근하지 않고
메모리에서 읽는다. 메모리는 SSD보다 약 1,000배 빠르다.

반면 풀스캔은 149.7MB를 읽어야 하므로 버퍼 풀을 초과한다.
스캔 도중 공간이 차면 앞서 올린 페이지를 밀어내고, 다음 실행에서 그 페이지가
다시 필요해 또 디스크를 읽는다. 그래서 2회차에도 개선되지 않았다.

캐시 효과는 2회차라서 나오는 것이 아니라,
**읽는 양이 버퍼 풀보다 작을 때만** 나온다. 1010ms → 1032ms가 그 반례다.

여기서 버퍼 풀 크기 자체가 병목임이 드러났다. 현재 128MB는 MySQL 기본값이고
데이터는 1.4GB다. 쿼리 튜닝만으로는 도달할 수 없는 영역이 있다는 의미이며,
`innodb_buffer_pool_size` 조정 효과는 별도로 측정할 예정이다.

### 인덱스의 비용

인덱스는 조회를 빠르게 하는 대신 두 가지 비용을 발생시킨다.

| index_name | pages | size_mb |
|---|---:|---:|
| PRIMARY | 9,580 | 149.7 |
| email | 4,144 | 64.8 |
| **idx_member_name** | **1,700** | **26.6** |

첫째, **저장 공간**이다. 컬럼 하나에 인덱스 하나를 추가해 26.6MB가 늘었고,
데이터 본체(149.7MB)의 약 18%에 해당한다.
`PRIMARY`가 149.7MB인 것은 InnoDB가 PK 순서로 데이터를 저장하기 때문이고,
`email`은 `UNIQUE` 제약으로 자동 생성된 것이다.

둘째, **쓰기 성능**이다. `INSERT` / `UPDATE` / `DELETE` 시 테이블뿐 아니라
인덱스도 함께 갱신해야 하므로 인덱스가 많을수록 느려진다.

따라서 인덱스는 많이 걸수록 좋은 것이 아니라, 실제 조회 패턴에 필요한 것만
선별해 만들어야 한다.

## Result

측정값은 모두 `EXPLAIN ANALYZE`로 2회 이상 실행한 뒤 2회차를 기록했다.

### 데이터 분포

| 항목 | 값 |
|---|---:|
| 전체 건수 | 1,000,000 |
| `member_name` 고유값 수 | 2,000 |
| 이름당 평균 건수 | 500 |
| 전체 대비 비율 | 0.05% |

### 인덱스 전후 비교

| 항목 | 인덱스 전 | 인덱스 후 |
|---|---|---|
| `type` | `ALL` | `ref` |
| `possible_keys` | `NULL` | `idx_member_name` |
| `key` | `NULL` | `idx_member_name` |
| `key_len` | - | 202 |
| `rows` (추정) | 990,615 | 500 |
| `filtered` | 10.00% | 100.00% |
| `Extra` | `Using where` | `NULL` |
| 실제 읽은 행 | **1,000,000** | **500** |
| 1회차 | 1010ms | 112ms |
| **2회차 (기록값)** | **1032ms** | **2.36ms** |
| 인덱스 크기 | - | 26.6MB |

**1032ms → 2.36ms, 437배 개선**

`key_len = 202`는 `VARCHAR(50) × 4바이트(utf8mb4) + 가변길이 표시 2바이트`다.
문자셋이 인덱스 크기에 직접 영향을 준다.

## Troubleshooting

### 측정 전 인덱스 상태를 확인하지 않아 전후가 뒤바뀔 수 있었다

`EXPLAIN`을 실행했을 때 `key = idx_member_name`이 나왔다.
`CREATE INDEX`를 실행하지 않았는데 인덱스가 사용되고 있었고,
이전 실습에서 생성한 인덱스가 남아 있는 상태였다.

이를 발견하지 못했다면 "인덱스 후" 값을 "인덱스 전"으로 기록해
개선 효과가 거의 없다는 잘못된 결론에 도달했을 것이다.

측정 절차의 첫 단계로 `SHOW INDEX`를 넣어 대상 상태를 확인하도록 수정했다.
